# Mises à jour des dépendances

Les montées de version relèvent de l'agent (point technique, [Prise de décision](../gouvernance/prise-de-decision.md)) : il les détecte et les traite sans attendre de demande de l'utilisateur. L'outillage décrit ici (épinglage, relevé, contrôle de sécurité quotidien) est mis en place par la Phase 3, sécurité et montées de version ([`suivi-implementation/`](../../suivi-implementation/index.md)) ; jusque-là, ses règles valent pour toute montée faite en chemin, et ce qu'elles supposent d'outillage est sans objet.

- **Toutes les technologies surveillées** : chaque version que le dépôt utilise est **épinglée** à sa valeur exacte, pour qu'aucune ne change sans une modification du dépôt, donc sans montée de version visible :
  - packages NuGet, centralisés dans `Directory.Packages.props`, et outils .NET locaux (`dotnet-tools.json`) ;
  - SDK .NET : version exacte dans les workflows, `global.json` n'en fixant que le minimum, pour les postes de développement ;
  - outils de construction de l'installeur (NSIS, dans `dotnet-desktop.yml`) ;
  - actions GitHub des workflows : empreinte complète du commit (*commit SHA*) de leur version exacte, cette version en commentaire (`uses: <action>@<empreinte> # v1.2.3`). Un tag de version reste déplaçable, par l'éditeur de l'action ou par qui compromet son dépôt, sauf pour une release immuable (documentation GitHub, *Immutable releases*), que peu d'actions publient : le code exécuté par les workflows, avec les secrets du dépôt, changerait sans modification du dépôt. Une empreinte, elle, ne désigne jamais un autre commit, et le relevé (ci-dessous) vérifie qu'elle est bien celle de la version du commentaire.
    - **Alternative écartée (tag de la version seul)** : un tag déplacé, comme l'ont été ceux d'actions compromises, fait exécuter un autre code sans rien dans le dépôt qui le montre ni en déclenche la revue.
- **Relevé par l'agent** (`scripts/Get-DependencyUpdates.ps1`) : à chaque reprise du travail, l'agent vérifie si le relevé est dû (au plus un par contrôle de sécurité quotidien, ci-dessous) et, s'il l'est, exécute ce script, qui interroge les sources officielles (NuGet, métadonnées de publication de .NET, versions publiées des actions GitHub et de NSIS). Il liste, pour chaque technologie épinglée, la version la plus récente de sa version majeure et, à part, la version majeure la plus récente, pour qu'une version majeure écartée (ex. une version de .NET qui n'est pas LTS) ne masque pas les correctifs de celle en usage ; chacune avec sa portée (corrective, mineure, majeure) et sa date de publication, ainsi que les vulnérabilités connues, sans rien modifier. Il s'arrête sur une action dont l'empreinte n'est pas celle de la version de son commentaire.
  - **Fréquence** : [Relevé des versions à la reprise du travail](releve-des-versions-a-la-reprise-du-travail.md).
  - **Aucun outil externe** : le relevé et le contrôle de sécurité n'emploient que les sources officielles, l'outillage du SDK .NET et la base des vulnérabilités de GitHub (*GitHub Advisory Database*), qui n'ouvre aucune PR. Aucun robot ne modifie le contenu du dépôt ni n'ouvre de Pull Request, le contrôle de sécurité ne tenant qu'un ticket : une montée est une Pull Request de l'agent, faite de ses commits signés.
    - **Alternative écartée (mises à jour de Dependabot, *version updates* et *security updates*)** : leurs PR, prêtes pour la revue dès leur ouverture, déclencheraient une revue Codex avant même la revue de l'agent ([Budget IA](../gouvernance/budget-ia.md)).
    - **Alternative écartée (Renovate)** : un outil externe de plus, doté d'un accès en écriture au dépôt, dont les commits ne seraient signés (`required_signatures`) que sous l'identité d'une application GitHub et de ses secrets ; son apport, ouvrir lui-même les PR, est sans objet : la montée n'est traitée qu'à la reprise du travail, par l'agent, qui fait sa revue et ses adaptations.
  - **Vulnérabilités connues** ([Suivi des versions et des vulnérabilités](../../contraintes-techniques/suivi-des-versions-et-des-vulnerabilites.md)), surveillées chaque jour, que le dépôt fasse ou non l'objet de travaux, par le contrôle de sécurité quotidien (`.github/workflows/security-audit.yml`), avec pour chaque technologie l'outil qui lit réellement les versions en usage :
    - packages NuGet, transitifs compris : audit NuGet (*GitHub Advisory Database*, `dotnet list package --vulnerable --include-transitive`), également exécuté par le relevé ;
    - actions GitHub : *GitHub Advisory Database*, interrogée pour chaque version en usage (API `advisories`, `affects=<action>@<version>`), celle du commentaire de son empreinte.

    Le contrôle tient la liste des vulnérabilités connues dans le ticket de suivi de son harnais (étiquettes `security-audit` et `harness`, [Issues](../revue-tickets/issues.md#tickets-de-suivi-des-harnais)), ouvert tant que la liste n'est pas vide, et que le relevé affiche. Il n'échoue que lorsqu'il trouve une vulnérabilité absente de cette liste : GitHub notifie alors l'échec à l'utilisateur qui a créé le workflow, une seule fois par vulnérabilité, et non chaque jour tant qu'elle reste sans correction.
  - **Correction dès qu'elle est disponible** : à chaque relevé, l'agent cherche, pour chaque vulnérabilité, une correction applicable (version corrigée d'un package) ; il l'applique en tête, sans attendre la montée mensuelle ni le délai de 7 jours. Une vulnérabilité sans correction disponible reste suivie par le contrôle jusqu'à la parution de sa correction.
  - **Aucun blocage par une vulnérabilité qu'on ne peut pas encore corriger** : le contrôle quotidien n'est pas un check requis, et l'audit NuGet n'est qu'un avertissement dans les constructions ; ni le développement ni la fusion d'une PR n'attendent donc une correction qui n'existe pas.
  - **Autres versions** : une montée par mois au plus, au premier relevé d'un mois qui n'en a pas encore connu : les versions mineures et correctives disponibles y sont réunies en une seule Pull Request, pour limiter les revues Codex et les exécutions du CI.
  - **Délai de 7 jours** avant de retenir une version tout juste publiée, pour qu'une version retirée ou corrigée aussitôt ne soit pas prise.
  - **Versions majeures** : celle d'une technologie de la stack est un chantier à part (ci-dessous) ; celle d'une autre dépendance rejoint la montée mensuelle.
  - **Hors de la revue Codex jusqu'à la revue de l'agent** : la Pull Request d'une montée est ouverte en brouillon ([Ouverture de la PR](../revue-tickets/revue-codex-bloquante.md#ouverture-de-la-pr)) ; l'agent ne la passe en « prête pour la revue » qu'une fois sa revue de l'existant faite (ci-dessous), ce qui déclenche la seule revue Codex de la montée.
- **Aucune montée sans sa revue** : toute montée de version, quelle qu'en soit la portée (correctif de sécurité compris), et quelle que soit la technologie (bibliothèque, SDK, outil, action GitHub…), est une montée de version au sens de [Exploitation des technologies retenues](../../contraintes-techniques/exploitation-des-technologies-retenues.md). Sa **revue de l'existant**, au regard de la nouvelle version, est donc une condition de sa fusion, au même titre que la non-régression et la revue Codex ([Règle de merge](../revue-tickets/regle-de-merge-non-regression-porte-de-qualite-et-revue-codex-obligatoires.md)) : l'agent la mène **avant** de passer la PR en « prête pour la revue », et une PR dont la revue n'est pas faite n'est pas fusionnée.
  - **Moment** : à chaque relevé, juste après lui et avant le chantier suivant du plan ; une alerte de sécurité passe en tête.
  - **Contenu**, pour chaque dépendance montée, à partir de ses notes de version et de la documentation officielle, depuis la version remplacée : changements de comportement, dépréciations et changements cassants qui touchent le dépôt, à corriger dans la PR ; nouveautés qui amélioreraient l'existant (performances, lisibilité, sécurité, concision, maintenabilité…), confrontées à l'usage réel qu'en fait le dépôt : gain réel, contre-vérification sur la documentation officielle.
  - **Proportion** : la revue suit la portée de la montée — les seules notes d'une version corrective, toutes les nouveautés d'une version mineure, l'ensemble de l'existant pour une version majeure.
  - **Trace** : la description de la PR, qui devient le corps du commit ([Conventions de commit](conventions-de-commit.md)) et que l'agent réécrit selon le template avant de la passer en « prête pour la revue », présente la revue dépendance par dépendance, et ses conclusions : correction faite dans la PR, chantier d'amélioration identifié (un ticket chacun, rédigé selon [Contenu d'un ticket](../revue-tickets/suivi-par-tickets.md#contenu-dun-ticket), réalisé par sa propre PR), ou absence de chantier, constatée explicitement.
- **Version majeure d'une technologie de la stack** ([Stack cible](../../contraintes-techniques/stack-cible.md) : runtime et SDK .NET, Windows Forms, et les bibliothèques structurantes de l'application, [Versions et bibliothèques](../../choix-implementation/versions-et-bibliotheques.md)) : la montée est un chantier, avec son ticket, qui porte la montée et son adaptation (PR de l'agent), puis, à sa fusion, le ticket de la revue de l'existant au regard de la nouvelle version. La décision d'y procéder et son moment relèvent de l'agent, dans le respect des versions retenues (ex. les seules versions LTS de .NET). Une montée qui a un impact visible pour les utilisateurs de l'application (prérequis d'installation, comportement) est annoncée à l'utilisateur ([Prise de décision](../gouvernance/prise-de-decision.md)).
- **Toute autre montée** (version mineure ou corrective, version majeure d'une autre dépendance : actions GitHub, outils et bibliothèques de test…) : traitée dans la PR de la montée, mensuelle ou de sécurité, revue et adaptations comprises, poussées tant qu'elle est en brouillon.
