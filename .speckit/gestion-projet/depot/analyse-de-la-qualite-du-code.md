# Analyse de la qualité du code

- **SonarQube Cloud** (organisation `tetram76`, projet `Tetram76_tvrename`, gratuit pour un dépôt public) analyse le code et sa couverture par les tests, sur chaque Pull Request et sur `main`. Ses indicateurs (porte de qualité, couverture, fiabilité, sécurité, maintenabilité…) sont affichés en tête du `README.md`, et il commente chaque Pull Request de son analyse.
- **Analyse de chaque push, indépendante de la non-régression** : elle porte sur la couverture des tests du push, sans qu'ils soient exécutés une seconde fois ([Intégration continue (CI)](integration-continue-ci.md)), et une analyse qui ne peut pas aboutir ne fait jamais échouer le contrôle de non-régression.
- **Porte de qualité, condition de fusion une fois rendue bloquante** ([Règle de merge](../revue-tickets/regle-de-merge-non-regression-porte-de-qualite-et-revue-codex-obligatoires.md)) :
  - **Porte non bloquante tant qu'elle n'a pas été rendue bloquante** (exigence de l'utilisateur) : ni son échec ni l'absence d'analyse n'empêchent la fusion d'une Pull Request, et le Ruleset ne requiert pas son check. L'analyse de chaque Pull Request reste traitée ([Analyse SonarQube Cloud](../revue-tickets/analyse-sonarqube-cloud.md)) : ses nouveaux problèmes sont corrigés, différés ou rejetés, et un échec de la porte est examiné, pour en connaître la cause, sans être une condition de la fusion. La Phase 2 a pour objet que l'ensemble du code réussisse la porte ([Phase 2](../../suivi-implementation/phase-2-nettoyage-du-code.md)).
  - **Porte rendue bloquante dès que l'état du code le permet, au plus tard à la fin de la Phase 2**, contrepartie de la règle précédente (exigence de l'utilisateur) : dès que l'ensemble du code réussit la porte, ce qui dépend de l'ordre dans lequel les chantiers de la Phase 2 sont réalisés, elle est rendue bloquante, sans attendre la fin de la phase ; la phase n'est pas terminée tant qu'elle ne l'est pas, si bien qu'aucune Pull Request d'une phase suivante n'est fusionnée sans elle. Elle est alors imposée par le Ruleset, qui requiert le check `SonarCloud Code Analysis` de l'application SonarQube Cloud ([Configuration du repository GitHub](configuration-du-repository-github.md)), et non le job du workflow : ce check reflète le verdict de la porte, et n'existe que si l'analyse a abouti. Une analyse qui n'aboutit pas, faute de service ou de jeton, bloque alors la fusion.
- **Seule analyse statique du code** (décision de l'utilisateur) : aucune autre analyse ne double celle de SonarQube Cloud. Ses alertes de sécurité apparaissent aussi dans l'analyse du code de GitHub (check `SonarCloud` de *code scanning*), qui ne fait que les reprendre.
  - **Alternative écartée (CodeQL, `codeql.yml` hérité du fork)** : son analyse de sécurité du C# double celle de SonarQube Cloud, pour un job plus long que la construction et les tests de la non-régression, sur chaque Pull Request et chaque semaine.
- **Dette de l'existant** : la porte ne juge que le nouveau code. Le code hérité du fork, qui n'a jamais été analysé, porte une dette que relève le [Contrôle qualité hebdomadaire](controle-qualite-hebdomadaire.md) et que résorbe la Phase 2, nettoyage du code ([`suivi-implementation/`](../../suivi-implementation/index.md)) : couverture de tests et réussite de la porte de qualité sur l'ensemble du code.
- **Retours** : ceux de SonarQube Cloud sont ceux d'un outil d'analyse statique, traités dans le cycle de chaque Pull Request selon [Analyse SonarQube Cloud](../revue-tickets/analyse-sonarqube-cloud.md).
- **Jetons** : l'analyse s'authentifie auprès de SonarQube Cloud avec le secret de dépôt GitHub `SONAR_TOKEN` ; l'agent, pour le marquage des problèmes et le paramétrage du projet, avec un jeton distinct, placé dans la variable d'environnement `SONAR_TOKEN` du poste ([Repository](repository.md)), pour que chacun se révoque sans toucher à l'autre. Une Pull Request venant d'un **fork** n'y a pas accès : son analyse échoue et elle ne peut pas être fusionnée en l'état. L'analyse automatique de SonarQube Cloud est désactivée sur le projet : elle exclut l'analyse par le CI, et ne mesure pas la couverture.
- **Périmètre** : le code de la solution, celui de `tests/` comme code de test ; les images de l'application, qui ne sont pas du code, ne sont pas analysées ; les fichiers générés par le concepteur Windows Forms (`*.Designer.cs`) et les ressources en sont exclus de la couverture, qu'aucun test unitaire n'exerce utilement. Les scripts PowerShell de l'outillage (`scripts/`) sont analysés, mais exclus de la couverture, que seuls les tests .NET mesurent. Le code dont le retrait est prévu (canal de mise à jour automatique, films et leurs collections, fonctions RSS et NZB : [Phase 4](../../suivi-implementation/phase-4-corrections-et-nouvelles-fonctionnalites.md)) est lui aussi exclu de la couverture, qu'on ne lui demande pas (exigence de l'utilisateur, [Phase 2](../../suivi-implementation/phase-2-nettoyage-du-code.md)) ; chaque exclusion disparaît avec le code qu'elle désigne.
- **Nouveau code** : celui qui a changé depuis la dernière version publiée ([Versions et releases](versions-et-releases.md)) : le projet est réglé sur la version précédente (*Previous version*), et chaque analyse porte le tag de la dernière version publiée ; la publication d'une version relance l'analyse de `main` pour que la période commence au commit publié. Sur une Pull Request, le nouveau code est celui de la PR.
